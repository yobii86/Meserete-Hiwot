## 3. NON-NEGOTIABLE DATA AND COMPATIBILITY RULES

### 3.1 Zero destructive migrations

- Never drop existing production tables.
- Never delete historical student, attendance, quiz, assessment or financial records.
- Never rename or remove existing production columns as a shortcut.
- Prefer additive migrations, nullable fields, safe defaults and backward-compatible indexes.
- Preserve `edu_question_banks`, `edu_quiz_draws` and their historical relationships.
- Preserve completed quiz attempts, answers, grades, certificates and rankings.
- Do not reset production data to make tests pass.
- Every migration must have a documented recovery strategy.

Before running any migration, inspect its impact and verify rollback and recovery options.

### 3.2 Backward-compatible API

Existing mobile versions 1.5.0–1.5.2 must continue functioning.

- Preserve existing endpoint contracts.
- Add new response fields without removing legacy fields.
- Maintain both `id` and `assessment_id` wherever required.
- Preserve existing response nesting, pagination, status codes and null-handling behavior.
- Do not return fabricated empty collections to conceal broken endpoints.
- Do not deprecate an endpoint until actual client dependencies are verified.

Create regression fixtures representing legacy API responses and test old-client compatibility against the updated backend.

### 3.3 Preserve authentication and authorization

Never weaken security to make a feature work.

Every protected API endpoint must independently validate permissions. Hiding a button in Flutter is not authorization.

Separate administrative capabilities, including:

- Global read access.
- Curriculum management.
- Lesson editing and publishing.
- Student and teacher management.
- Assessment and grade management.
- Attendance management.
- Signature viewing and exporting.

Do not grant global write permissions simply because someone has an administrator-related role.

Execute the following engineering work packages in dependency order.

### WORK PACKAGE 2 — CURRICULUM AUTHORIZATION

**Objective:** Implement secure, role-aware curriculum access without locking out legitimate users.

Implement the following authorization hierarchy using actual roles and permissions:

1. Authorized Super Admin / Education Director: global access according to granted permissions.
2. Assigned Teacher: access to assigned courses, subjects and classes according to permissions.
3. Enrolled Student: access to subjects associated with valid active enrollment.
4. Historical Student: read-only access to permitted previous-year materials and records.
5. Public Content: accessible when explicitly marked public.
6. Unenrolled Student: friendly orientation screen without access to restricted curriculum.

Handle:

- Students transferred between classes.
- Multiple simultaneous enrollments.
- Teachers who are also students.
- Pending student assignments.
- Historical enrollments.
- Multiple academic years.
- Unauthorized direct API requests.

Implement a centralized authorization service rather than duplicating inconsistent checks throughout controllers.

**Security requirement:**

The `EDU_STRICT_CURRICULUM_GATE` rollback mechanism must never restore known insecure legacy authorization behavior.

If the new gate fails, use a verified secure fallback. If no safe fallback exists, deny restricted access and log the incident.

**Acceptance criteria:**

- Authorized users can access their permitted materials.
- Grade 7 students cannot access restricted Grade 8 curriculum.
- Teachers cannot edit courses outside their permissions.
- Historical records remain accessible according to policy.
- Unenrolled users receive an appropriate orientation experience instead of an unexplained blank screen.

### WORK PACKAGE 3 — QUESTION BANK DEPRECATION AND QUIZ INTEGRITY

**Objective:** Allow direct course quiz execution without damaging existing question bank data.

Tasks:

1. Inspect the existing question bank and direct quiz relationships.
2. Preserve all question bank and quiz draw tables.
3. Identify active quizzes still dependent on question banks.
4. Inspect historical attempts and answer snapshots.
5. Update quiz execution to use direct `quiz_id` questions where the quiz is configured for direct execution.
6. Preserve historical question snapshots and grading behavior.
7. Ensure active attempts can finish safely.
8. Prevent accidental duplication of questions.
9. Verify assessment creation, publication, attempts, submission and result calculations.
10. Maintain historical quiz reporting and student certificates.

Do not switch existing question-bank-dependent quizzes to a new execution path without verifying that their existing questions and attempts remain valid.

**Acceptance criteria:**

- Old question bank records remain intact.
- New direct quizzes work.
- Existing attempts remain readable.
- Existing marks do not change unexpectedly.
- No historical answer or grading information is lost.

### WORK PACKAGE 4 — DASHBOARD CACHE AND DATABASE PERFORMANCE

**Objective:** Protect the application during peak Sunday-school usage.

Implement a reliable dashboard cache strategy.

Requirements:

1. Use a cache key that accounts for user identity and relevant enrollment or permission changes.
2. Implement atomic locking for cache recomputation.
3. Recheck the cache after acquiring the lock.
4. Release locks safely.
5. Handle lock contention without triggering duplicate expensive computations.
6. Prevent stale dashboard information from persisting after important data changes.
7. Invalidate relevant caches after enrollment, assessment, attendance and curriculum updates.
8. Support a safe cache-disabled mode for troubleshooting.

Do not use nested cache operations that fail to coordinate cache misses correctly.

Do not assume Redis exists without checking the actual hosting configuration.

If Redis is unavailable, implement a documented alternative compatible with the production environment.

**Acceptance criteria:**

- Concurrent dashboard requests do not cause uncontrolled recomputation.
- Cache invalidation works.
- Permission changes do not leave unauthorized cached data accessible.
- Dashboard results remain accurate.

### WORK PACKAGE 5 — OFFLINE ATTENDANCE SYNCHRONIZATION

**Objective:** Make offline attendance synchronization reliable, auditable and idempotent.

Implement:

1. Deterministic attendance session identification using program, schedule and session date.
2. Unique idempotency identifiers for offline synchronization records.
3. Server-managed record revisions or equivalent optimistic concurrency control.
4. Safe synchronization of offline batches.
5. Conflict detection when multiple devices or administrators update the same attendance record.
6. Immutable audit history for changes and conflicts.
7. Duplicate submission prevention.
8. Partial-batch recovery.
9. Retry-safe synchronization.
10. Clear synchronization status for Flutter users.

**Critical conflict-resolution rule:**

Do not trust client timestamps as the sole authority for deciding which attendance record wins.

Do not automatically overwrite an administrator's authoritative update because an offline device reports a later local timestamp.

Use revision comparison and explicit conflict handling. Preserve both versions and record the resolution decision.

Audit records must include, where available:

- Session ID.
- Member ID.
- Previous status.
- New status.
- Actor ID.
- Device identifier.
- Idempotency key.
- Server timestamp.
- Conflict resolution result.

**Acceptance criteria:**

- Repeated synchronization does not create duplicates.
- Concurrent updates do not silently destroy information.
- Conflicts are auditable.
- Interrupted batches can resume.
- All successfully accepted attendance changes are reflected consistently.

### WORK PACKAGE 6 — FFMPEG MEDIA MIGRATION AND QUEUE RESILIENCE

**Objective:** Process media without exhausting server resources or disrupting API availability.

Tasks:

1. Inspect existing media storage and conversion workflows.
2. Verify FFmpeg installation and execution permissions.
3. Implement persistent migration job records.
4. Process files through controlled background workers.
5. Set configurable worker concurrency and per-file timeouts.
6. Prevent duplicate processing.
7. Implement retry and failure states.
8. Detect already-converted files.
9. Preserve original files until successful verification.
10. Verify output file integrity before marking migration complete.
11. Handle worker restarts.
12. Handle Redis or queue unavailability.
13. Provide safe recovery for interrupted migrations.

Use `--concurrency=1` as an initial conservative setting only if compatible with the hosting environment.

Do not claim a specific CPU ceiling without measurement.

Do not move expensive FFmpeg processing into normal web requests as an automatic fallback.

If background processing is unavailable, preserve the pending job and expose a controlled recovery mechanism rather than overwhelming the API server.

**Acceptance criteria:**

- Jobs survive worker restarts.
- Duplicate jobs do not create duplicate conversions.
- Failed jobs can retry safely.
- Original media remains recoverable.
- API performance remains within measured acceptable limits.

### WORK PACKAGE 7 — UNENROLLED STUDENT EXPERIENCE

**Objective:** Prevent new or unassigned students from encountering a dead-end screen.

Implement an attractive orientation experience consistent with the existing Education UI architecture.

Requirements:

### WORK PACKAGE 8 — ROLLBACK AND FEATURE FLAGS

Implement safe rollback mechanisms for each work package.

Requirements:

- Feature flags must be controlled and validated on the backend where security-sensitive.
- Disabling a new feature must not delete associated data.
- Old and new workflows must not corrupt each other's records.
- Preserve the legacy attendance interface until the new attendance workflow is verified.
- Preserve the legacy magazine quiz editor until the unified editor passes regression tests.
- Disable dashboard caching safely without changing authorization.
